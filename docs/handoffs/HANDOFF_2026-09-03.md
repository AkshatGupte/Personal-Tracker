## 2. The theme, in one page

Full detail is in `CLAUDE.md` under *Visual Design Direction*. The parts most
likely to be broken by accident:

- **`font-sans` and `font-display` are both Archivo, deliberately.**
  `font-display` is applied to Track names and page headings — i.e. to *user
  content*. Pointing it at Bangers would set someone's Track and Topic names in
  a comic face. Bangers is `font-comic`, never inherited, and is currently used
  in exactly two places: the nav wordmark and the "No tracks yet" empty state.
- **This palette has no green.** `positive` — "checked in today" — is cyan
  (`#00E5FF`). Reaching for a green means you are re-introducing the retired
  system. `accent` is magenta (volume/active), `streak` is yellow
  (consistency/milestones).
- **`Panel` has two registers and the choice carries hierarchy.**
  `variant="band"` is the workhorse; `variant="comic"` is spent **at most once
  per screen**. A page where everything is a comic panel has no hierarchy left.
- **The atmosphere is mounted once** in `app/layout.tsx`. Never draw it per
  screen.

## 3. Traps that already cost time

These are all in `CLAUDE.md` too, but they cost real debugging this session.

**The page ground is painted on `html`, never on `body`.** `html`'s background
propagates to the canvas. If `body` paints one as well, the `-z-10` atmosphere
layer renders *behind* it and is invisible. The symptom is a page that looks
flat black no matter how far the glow opacities are turned up.

**Never apply an SVG filter to a whole route subtree.** The route transition
originally drove `filter: url(#sv-chromatic-heavy)` across every page. It is a
per-pixel filter over an entire tree, and with `animation-fill-mode: both` its
0% state — *filter on* — applies during **any** delay before the animation runs.
During dev-mode route compilation the entire page sat fully ghosted and
unreadable. `app/template.tsx` is now transform + opacity only.

**A `clip-path` clips the element's own `box-shadow` away with it.** That is why
a wobbled `Panel` draws its registration plate as a real sibling. It also cannot
be a *child*: the panel paints its own background, so a negative-z child would
render behind that background and never be seen.

**Editing `app/globals.css` with regex is how the build broke.** Stripping the
motif blocks left two orphaned unterminated `/*` openers, which swallowed
`:root`'s closing brace. If you do bulk CSS edits, check both braces *and*
comment balance afterwards:

```bash
python3 -c "
import re;s=open('app/globals.css').read()
print('stray /*:', s.count('/*')-s.count('*/'))
t=re.sub(r'/\*.*?\*/','',s,flags=re.S)
print('braces:', t.count('{')==t.count('}'))"
```

## 5. The product model — investigated, and it is sound

A full read-only audit of the schema, completion engine, PRD and roadmap was run
this session. **Do not redo it.** The conclusions:

**Rendred is correctly specified and modelled as a persistent daily learning
system.** Tasks are persistent recurring activities; the same Task checks in on
many days; `Task.status` and `Task.completedAt` are fully removed from code and
schema and survive only as deliberate historical record in `DECISIONS.md` and
`ROADMAP.md`.

The derivation chain, one way only:

```
TaskCheckIn  (task × day)   ground truth — the row's existence IS the state
   ↓ derived
CompletionLog (track × day) rollup, rebuildable, never frozen history
   ↓ cached
Track.currentStreak / longestStreak / lastActivityDate
```

`lib/completion.ts` is the single write path and is **recompute-never-increment**
— that is what makes double-clicks, retries and undo→redo harmless.

**No schema change is required for the core loop.** It already works.

### The one real gap

The *model* is complete. The **reinforcement half of the loop is not** —
specifically, nothing distinguishes *extending a streak* from *merely recording
a day*, which is the thing that gives someone a reason to return tomorrow.

**The key finding:** `recomputeToday()` already returns a full `StreakSummary`,
and `setCheckIn` **discards it**:

```ts
// lib/actions/tasks.ts, in setCheckIn
await recomputeToday(tx, task.topic.trackId, now);  // returns StreakSummary
return task.topic.trackId;                           // ...thrown away
```

The app already computes the exact fact the loop needs and drops it.

### Misleading names to be careful of (no behavioural defect)

- `CompletionLog.tasksCompletedCount` — "Completed" reads terminal. It means
  *check-ins recorded for this track that day*. The single most likely field to
  mislead someone into re-introducing one-time-task semantics.
- `Track.lastActivityDate` comment and `docs/SCHEMA.md:19` both say "completed"
  where they mean "checked in".

## 6. Immediate next step

Roadmap Phase 2, **"The check-in moment"** — the only unchecked item that is not
blocked on something else. Phase 3 (LLM) is gated until Phase 2 is functionally
complete.

**Start by settling one product question, before writing any code:**

> What counts as *extending a streak*, as opposed to merely recording a day?
> Specifically: is day 1 of a new streak an extension? What about re-checking a
> day that was already checked? Does an undo followed by a re-check count again?

Everything else in the loop is either already correct or blocked on that answer.
Once it is settled, the minimum work is:

1. Capture the streak before/after in `setCheckIn` and **return** it instead of
   discarding it. No schema change — the value already exists.
2. Make the check-in read as **one composed outcome** rather than four
   independent updates (tick, ring, elevation, streak).
3. Only then design how "extended" reads differently from "recorded" — **inside
   the frozen Spider-Verse system**. The vocabulary already exists: yellow means
   streak, cyan means checked-in-today.

**Do not add** XP, points, levels, badges, coins, streak freezes, reminders,
leaderboards, or daily goals/targets. The first six are explicit PRD non-goals
or violate `lib/streak.ts`'s stated rule that no forgiveness may be added.
Daily goals are the only one with a plausible case — commitment reinforcement is
the single missing behavioural pattern — but it is a *new product concept*. Do
not reach for it to compensate for the unbuilt check-in moment. Build that
first, then re-evaluate.

Two smaller items are also open, if the check-in moment is blocked:

- **Monthly summary view** — the cheapest thing on the board. `lib/rollup.ts`
  already has `weekBuckets`; this needs `monthBuckets` beside it.
- **`docs/DEV_REPORT.md` was not updated** for the theme integration.
  `CLAUDE.md` calls that mandatory after any meaningful change.
